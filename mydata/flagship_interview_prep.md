### Model answers

**Q1. Why defer WebGL init by one `requestAnimationFrame`, and why pair `renderer.dispose()` with `forceContextLoss()`? (React StrictMode double-mount)**

In dev, React StrictMode mounts a component, immediately unmounts it, then remounts it, to surface unsafe effects. My build effect creates a real `WebGLRenderer`, which grabs a GPU context. Without protection, the throwaway first mount creates a context, its cleanup runs `forceContextLoss()` on it, and then the *real* mount tries to create another context right after — and the browser blocks it with "a WebGL context was lost because it caused context loss and was blocked." You end up with a dead canvas.

My fix is in `WireframeGlobe.tsx`: the effect doesn't create anything synchronously. It schedules `start()` inside a `requestAnimationFrame` (`startRaf`), and captures a `cancelled` flag. If StrictMode unmounts before that frame fires, the cleanup sets `cancelled = true` and cancels the rAF, so the throwaway pass never does *any* GL work — no context is ever created or lost on it. Only the surviving mount actually builds.

On the disposal side, `renderer.dispose()` frees Three.js's internal resources but does *not* release the underlying GL context — the browser keeps it alive, and browsers cap you at a handful of live contexts. So I call `renderer.forceContextLoss()` right after to actually hand the context back. On a page with two heavy scenes, leaking contexts on every route change would eventually exhaust the pool and blank the canvas. The comments in both files call this out explicitly — it's the thing that makes the scenes survive real navigation.

**Q2. Why do country hover-picking in geo space (raycast sphere → invert quaternion → point-in-polygon) instead of GPU picking or raycasting the border meshes? Trade-offs — antimeridian seam, throttling?**

Two reasons. First, my borders are *lines*, not filled meshes — I batch all the world's country outlines into one `LineSegments` for one draw call. You can't raycast-hit-test the *interior* of a country when you only have its outline as line geometry; there's no surface to hit. Second, GPU/color picking would mean a second render pass with a picking material and a `readPixels` per hover — a pipeline stall — just to know which country the cursor is over.

So instead I raycast the pointer against a single invisible unit `Sphere` (`_hoverSphere`), which is cheap and exact. That gives me the 3D hit point in world space. The globe rotates as a group, so I invert the globe's quaternion (`_hoverInvQ`) and apply it to the hit point to get the point in the globe's *local* frame, then `vec3ToLatLon` converts to lat/lon. From there it's a classic ray-casting point-in-polygon (`pointInRing`) over the GeoJSON rings — the exact same data I drew, so the highlight always matches the borders.

Trade-offs I made deliberately: I throttle hover to ~20fps (`if (now - lastHoverMs < 50) return`) because point-in-polygon over every feature isn't free and hover doesn't need 60fps. The antimeridian is guarded when *building* geometry — `if (Math.abs(a[0] - b[0]) > 180) continue` skips segments that wrap the seam so I don't draw a line across the whole globe. And I only test outer rings, so enclaves aren't perfect — fine for a decorative highlight, and it kept the whole thing on the CPU with zero extra GPU passes.

**Q3. In the blog gallery you `lerp` each card between a flat pose and a sphere pose and `wrap()` positions toroidally so the grid is "infinite." How does `wrap()` guarantee no duplicate card is visible at once, and how did you size `COLS/ROWS` vs FOV?**

The grid is a torus: I lay out `COLS × ROWS` unique cards (9 × 6 = 54), and `wrap(v, S) = ((v % S) + S) % S - S/2` folds any panned coordinate back into a single centered period `[-S/2, S/2)`, where the period is the full grid extent — `GRID_W = COLS * CELL_W` horizontally, `GRID_H = ROWS * CELL_H` vertically. Because each card's wrapped position is unique *within one period* and the visible viewport is smaller than one period, you only ever see one instance of a given card. The duplicate copies effectively live one full period away, off-screen, and slide in exactly as the original slides out — that's what makes it feel infinite instead of looping.

So the "no duplicate visible" guarantee is really a sizing constraint: one period (`GRID_W`, `GRID_H`) has to be wider and taller than what the camera can see at `FLAT_DEPTH`. That's why the FOV work matters. I derive vertical FOV from a fixed *horizontal* target — `HFOV_TARGET = 78°`, clamped 48–92 in `computeFov` — so horizontal card density stays constant from ultrawide down to a phone. I tuned `COLS/ROWS`, `CARD_W`, and `GAP` against that horizontal field so a full period always overfills the frame. If I'd let the horizontal FOV grow on wide screens, the viewport could exceed one period and you'd catch two copies of the same card — which is exactly the bug the fixed-HFOV approach prevents.

**Q4. The radar chart keeps a stable `key="detail"` under `AnimatePresence mode="wait"` instead of keying by dimension id. Explain the remount-vs-update trade-off and how "Voronoi-by-angle" avoids dead zones.**

`AnimatePresence mode="wait"` fully unmounts the exiting element and waits for its exit animation before mounting the next. If I'd keyed the detail card by dimension id (`key={activeItem.id}`), then moving from one dimension to another would be a *remount*: full exit tween on the old card, then full enter tween on the new one, back to back — a visible stutter every time you slide across the chart, which is the common motion. Instead I use one stable `key="detail"` for whichever dimension is active (`YourPassportMeasured.tsx`, line 524). Framer Motion then treats it as the *same* element with changing props, so React reconciles the text in place — the score, bar, and description update without a remount. The only real presence transitions are detail↔default (empty state), which are rare, so `mode="wait"` there is fine. Net: smooth glide between dimensions, clean fade to the empty state.

For the hover mapping — the 8 node dots are tiny, so per-dot hit areas leave dead zones between them where the card would collapse back to the default panel and flicker. So in `handlePointerMove` I make the *whole SVG* one hover surface: I take the cursor's vector from center, `Math.atan2(dy, dx)`, rotate so "up" is 0, and round to the nearest of N sectors — `((Math.round((ang / 2π) * N) % N) + N) % N`. That's a Voronoi partition by angle: every point in the chart maps to its nearest dimension, no gaps. I only bail near dead-center (`Math.hypot < 14`) where "nearest" is meaningless, and keep the last selection.

**Q5. `LoaderProvider` gates the splash on the hero's `onLoad` with a `MIN_DISPLAY_MS` floor and `SAFETY_TIMEOUT_MS` ceiling, and resets scroll via `useLayoutEffect`. Why `useLayoutEffect` not `useEffect`, and how do you keep the machine correct on a Candidates↔Companies toggle mid-load (stale hero)?**

`useLayoutEffect` fires synchronously *after* DOM mutations but *before* the browser paints; `useEffect` fires after paint. On a route change I need to reset scroll to top under the overlay — if I did that in `useEffect`, the browser would paint one frame at the old scroll position first, so you'd see a flash of the previous page scrolled down before it snaps up. In `useLayoutEffect` (line 110) the `window.scrollTo(..., "instant")` lands before paint, so the old position never shows. `instant` also overrides the global `scroll-behavior: smooth` so it doesn't animate.

The floor/ceiling are a UX guard: `MIN_DISPLAY_MS` (550ms) means the splash never *flashes* on a fast/cached load, and `SAFETY_TIMEOUT_MS` (4000ms) means a slow or broken hero image can never hang the splash forever — `armSafety` schedules an unconditional `lift`.

The stale-hero case is the subtle one, and it's handled in two places. Each hero reports readiness *with its route* (`reportHeroReady("/candidates")`), and `LoaderProvider` tracks `expectedHero`. On a toggle, `beginToggle` sets `expectedHero` to the new target, resets `heroReady = false`, restamps `startedAt`, and goes to `"transition"`. Then in `reportHeroReady` I guard `if (route !== expectedHero.current) return` — so a late `onLoad` from the *old* hero can't lift the new splash. Only the hero that matches the current intent counts. There's also a real-world edge I handled: a cached image may not fire `onLoad` after hydration, so `CandidateHero` also checks `el.complete` in the ref callback and reports ready that way — otherwise the splash could wait on a decode event that already happened.

**Rapid-fire follow-ups the interviewer might ask next (with 1-line answers):**
- *Why an opaque occluder sphere instead of depth-testing the far borders away?* The borders are transparent lines with `depthWrite: false`, so a black `MeshBasicMaterial` sphere at `R_OCCLUDER = 0.985` just physically hides the far hemisphere — simpler and cheaper than sorting transparent line depth.
- *Why keep `activeIndex` out of the build effect's deps and push it in imperatively via `apiRef`?* Rebuilding the whole globe on every hover would be catastrophic; the effect depends only on `[markers]`, and a tiny second effect calls `apiRef.current.setActive(activeIndex)` to drive the quaternion focus tween without touching geometry.
- *How do you keep marker glow from `AdditiveBlending` fighting the depth buffer?* The glow sprites use `depthTest: false` and `depthWrite: false` so they always composite on top, and the front/back fade is computed on the CPU from the normal·camDir dot in the render loop.
- *If you added the backend tomorrow, what changes?* Only `handleSubmit` — swap the `console.log` for a `fetch` to a Next.js route handler (or a form service) with optimistic UI; the validation, toast, and `slot-text` button states already exist, so it's a contained change.
- *Why canvas-texture the blog cards instead of HTML/CSS overlays?* To live inside the WebGL scene and bend onto the sphere per-card, each card has to be a texture on a `PlaneGeometry`; I draw the whole card (image, gradients, Playfair/Inter text) to a 640×832 canvas with mipmaps and max anisotropy so it stays crisp when it curves and recedes.

## 5. Kore — Interview Prep

**60-second pitch (say this first, first person):**
Kore is a zero-budget, real-time collaborative workspace I built solo — it folds Notion-style docs and databases, Google Keep-style notes, Excalidraw whiteboards, and team chat into one Next.js 16 app running entirely on free tiers, Vercel Hobby plus Supabase free. The hardest thing I built is the real-time layer. Rather than pay for a Yjs sync service, I hand-rolled a Yjs-CRDT provider over Supabase Realtime's private broadcast channels — it does a state-vector handshake on join, chunks payloads over 100 KB, debounces snapshots into a `bytea` column, and runs a reconcile loop to recover dropped broadcasts. The second hard part is security: 26 tables, Row-Level Security on every one, `SECURITY DEFINER` helper functions to dodge policy recursion, and I even gate the realtime channels themselves with RLS on `realtime.messages`. It shipped across six sequential build phases, all 16 commits mine.

**Lead with / emphasize:**
- The custom Yjs provider (`lib/yjs/provider.ts`) — I leaned on the CRDT guarantee (commutative, idempotent updates) so I could treat the network as lossy and unordered, which is what made a broadcast-only transport safe.
- Defense in depth on authz: `proxy.ts` is *optimistic only*, the DAL (`lib/dal.ts`, `requireMember`) is the real server-side gate, and RLS is the last backstop at the database — three independent layers.
- I extended RLS *past* the tables onto the realtime transport: policies on `realtime.messages` key off `split_part(realtime.topic(), ':', 2)` so channel subscription itself is membership-gated.
- The JSONB-cell concurrency fix: single-cell edits route through targeted `jsonb_set` RPCs (`db_set_cell`) instead of read-modify-write, so two people editing different cells of one row merge at the DB instead of clobbering.

**Own these honestly (caveats / traps an interviewer may probe):**
- Snapshot persistence is genuinely last-writer-wins on the `state bytea` column — I'll say plainly it's LWW, but explain *why that's safe*: every snapshot is a full CRDT-merged state, and a stale writer is corrected by the reconcile handshake pulling peers' newer updates back in. It's durability-of-the-latest-merge, not correctness-by-locking.
- No offline persistence — the doc lives in memory plus the server snapshot. If every peer disconnects before the debounced flush lands, the last ~2.5s of edits (`SNAPSHOT_DEBOUNCE`) can be lost. I mitigate with a flush on `destroy()`/unload, but I won't claim it's bulletproof.
- It's scoped to a single sub-10-person team on free tiers. I designed the schema multi-workspace-ready (helpers already take `p_workspace`), but I haven't load-tested broadcast fan-out at scale — I'd be honest that's untested territory, not a solved problem.

### Model answers

**Q1. Why buffer live updates during load, apply the snapshot, then flush and handshake — and what breaks if you apply live updates before the snapshot?**

The ordering is in `loadInitial()`. When the channel subscribes I set `buffering = true`, so any `y-update` broadcast that arrives goes into a `pending` array instead of the doc — see `onUpdate`, which checks `this.buffering`. Then I `await loadSnapshot`, `Y.applyUpdate` it with the `REMOTE` origin, flip `buffering = false`, replay every pending update, and only then call `requestState()` to handshake.

Honestly, because Yjs updates are commutative and idempotent, applying a live update *before* the snapshot wouldn't corrupt the doc — order genuinely doesn't matter to the CRDT. So the buffering isn't strictly for correctness; it's to avoid a subtle waste-and-flicker problem. If a live update landed first and referenced structure the snapshot hadn't introduced yet, Yjs would stash it as a pending struct until its dependency arrived, and the editor could render a half-formed intermediate state. Buffering guarantees the snapshot — the big baseline — is the *first* thing applied, so every incremental update lands on a complete base in one clean pass. The `REMOTE` origin (a module-level `Symbol`) is the load-bearing part: my `handleLocalUpdate` early-returns when `origin === REMOTE`, so applying network updates never re-broadcasts them and I never loop. Then `requestState()` sends my state vector so any peer replies with only what my snapshot was missing. Why it mattered: it let me trust a lossy broadcast transport without a central ordering server.

**Q2. You persist as one LWW `bytea` snapshot via `save_yjs_snapshot`, not an append-only log. Trade-offs, and how does reconcile + state-reply protect against a stale snapshotter?**

Right — `saveSnapshot` calls the `save_yjs_snapshot` RPC, which does `Y.encodeStateAsUpdate` of the *whole* doc and `on conflict do update set state = excluded.state`. It's one row per doc in `yjs_documents`, last-writer-wins. The trade-off I made consciously: an append-only update log is the textbook-durable choice — you never lose an intermediate op — but it needs compaction, it grows unbounded, and reads become "fetch and merge N rows." For a sub-10-person team on Supabase free, a single full-snapshot blob is dramatically simpler: one read on load, one debounced write, `bytea` so there's no base64 inflation and it's opaque to Postgres.

The thing that makes LWW safe here is that a snapshot is never a partial diff — it's always a *complete CRDT merge*, so a concurrent overwrite can't corrupt structure, it can at worst be slightly behind. The reconcile timer (`RECONCILE_INTERVAL`, 25s) plus the handshake is what catches "behind." On join and every 25 seconds, `requestState()` broadcasts my state vector; a peer's `onStateRequest` computes `Y.encodeStateAsUpdate(doc, theirSV)` — the exact delta I'm missing — and replies. So even if I snapshotted stale state, or my last broadcast got dropped, the next reconcile pulls the missing ops from any live peer and my next flush writes the corrected merge. The real gap I own: if *all* peers leave before the 2.5s debounce fires, un-flushed edits are lost — which is why `destroy()` awaits a final `flushSnapshot()`.

**Q3. Cells live in one JSONB `data` blob per row, but single-cell edits go through `db_set_cell` / `db_set_row_group`. Why not `update ... set data = ...`, and how does it affect two members editing the same row?**

Because a plain `update set data = {...}` is a read-modify-write of the *entire* JSONB object, and that's a lost-update race. If Alice and Bob both load row X, Alice sets the Status cell and Bob sets the Assignee cell, whoever writes second serializes their whole in-memory `data` back and silently erases the other's cell — even though they touched *different* keys. Since all of a row's cells share one `data jsonb` (flexible storage, no EAV table), that collision is very real.

So I push the mutation into the database as a *targeted* write. `db_set_cell(p_row_id, p_key, p_value)` runs `jsonb_set(data, array[p_key], p_value, true)` server-side — or `data - p_key` to clear — so it only rewrites the one key and leaves the rest of the blob untouched. Two members editing distinct cells of the same row now merge at the DB instead of clobbering; last-write only wins *per key*, which is the semantics you actually want. `db_set_row_group` does the same for a board drag — it sets the grouping cell and the view's order in one atomic partial write. Two important details I'll call out: these are `SECURITY INVOKER`, so the `database_rows` RLS still gates which row you can touch — a foreign workspace's row id just updates 0 rows. And in the `setCell` Server Action I re-resolve the property and row scoped to `membership.workspaceId` *before* the RPC, so it's IDOR-safe on top of RLS.

**Q4. `proxy.ts` is "optimistic only" and the DAL is the real authz boundary because Server Actions bypass the matcher. What's the attack, and how do `requireMember` + RLS give defense in depth?**

The attack is trusting middleware for authorization when it doesn't run on every code path. In Next.js, Server Actions are POSTs that execute *outside* the `proxy.ts` matcher — my `updateSession` only does optimistic session refresh and login redirects; it never sees the action invocation. So if the middleware were my authz gate, an attacker who's authenticated but *not* an active member — say a pending invite, or someone who was removed — could call a Server Action directly and mutate data, because nothing in the request path re-checked membership. Middleware is also purely session-level; it has no notion of workspace roles.

So I run three independent layers. First, every mutating Server Action starts with `await requireMember()` from `lib/dal.ts`, which calls `verifySession()` then `getActiveMembership()` and redirects unless there's an `active` membership row — and it stamps `workspace_id` from that membership, *never* from client input, so you can't spoof which workspace you're writing to. `requireOwner()` adds the role gate for destructive ops. Second layer is RLS: every table has policies like `is_workspace_member(workspace_id)`, so even if a bug skipped the DAL check, the database itself rejects the write. Third, IDOR guards like `databaseInWorkspace()` re-resolve object ownership server-side. The DAL is the *primary* boundary; RLS is the backstop that assumes my application code has bugs. Why it mattered: no single layer is trusted alone.

**Q5. RLS uses `SECURITY DEFINER` helpers to avoid recursion, and you gate realtime channels via `realtime.messages` policies keyed off `split_part(realtime.topic(), ':', 2)`. Walk through how a malicious member can't subscribe to another workspace's doc channel.**

Two pieces. The recursion problem first: the `memberships` table needs an RLS policy, but "can you read memberships" is itself a membership check — a naive policy that queries `memberships` inside the `memberships` policy recurses infinitely. So membership checks go through `is_workspace_member`, which is `SECURITY DEFINER` with `set search_path = ''`. Because it's definer-rights, its internal `select` from `memberships` bypasses RLS, so the policy never re-enters itself. Every table's policy calls that one helper instead of inlining a subquery.

For channels: my provider names topics `doc:{workspaceId}:{docType}:{docId}` (see the `topic` in the constructor). Supabase's Realtime Authorization runs RLS on the `realtime.messages` table for private channels, so I added `kore_realtime_read_channels` and `kore_realtime_write_channels` policies. They take `realtime.topic()`, pull segment 2 with `split_part(realtime.topic(), ':', 2)::uuid` — that's the workspace id — and require `is_workspace_member(...)` on it. So when a member of workspace A tries to subscribe to `doc:B:...`, the topic's segment-2 is B's id, the helper returns false because they have no `active` membership in B, and the `SELECT` policy denies the subscription outright — they never receive a single broadcast frame. And because `setAuth` pushes the user's JWT into Realtime before `subscribe()`, `auth.uid()` inside the helper is the real caller. Same policy covers `presence:{workspaceId}`. The transport is gated by the exact same helper as the tables — one source of truth.

**Rapid-fire follow-ups the interviewer might ask next (with 1-line answers):**
- *What stops the local update loop?* The `REMOTE` `Symbol` origin — `handleLocalUpdate` returns early when `origin === REMOTE`, so applied network updates are never re-broadcast.
- *Why base64 at the RPC boundary but `bytea` in the table?* The wire/JSON layer needs text (base64 in `save_yjs_snapshot`/`load_yjs_snapshot`), but at rest I `decode(...,'base64')` to `bytea` to avoid the ~33% inflation and keep it opaque.
- *Why 100 KB chunk limit?* Supabase broadcast caps around 256 KB; `CHUNK_LIMIT = 100_000` base64 chars leaves headroom, and `onChunk` reassembles by `cid`/index before dispatching.
- *Why two realtime systems?* Collaborative text needs CRDT merge (Yjs over broadcast); structured data — notes, databases, chat — is fine with Postgres Changes + a debounced refetch, which is simpler and RLS-filtered per subscriber.
- *Could a `person` cell be set to a non-member?* No — `setCell` runs `invalidPersonIds` against the workspace roster before the RPC and rejects it.

### Model answers

**Q1. Why the invisible `[[SIGN:<slotKey>]]`-anchor approach — render, re-parse with `pdfjs-dist`, stamp with `pdf-lib` — instead of computing signature placement at render time? What edge cases does it handle?**

The core problem is that our PDFs are dynamic: proposals have a variable number of faculty advisors, and the document content is generated from React-PDF TSX templates, so I can't know where "Faculty 3's signature box" lands on the page ahead of time. I decided to make the template the single source of truth for placement. Each signature location is just an invisible text marker — `[[SIGN:faculty_2_signature]]` — rendered in the template. After the PDF is generated, `pdf-anchor-locator.service` loads it with `pdfjs-dist`, walks the text layer character by character, and finds every anchor. We persist each one's page and bounding box as a `DocumentSlot` row keyed by `slotKey`. Then on each approval, `signature-embedding.service` white-boxes that anchor area and stamps the approver's signature image at the stored coordinates with `pdf-lib`, preserving aspect ratio. The edge cases that justified the extra parse pass: anchors get fragmented across multiple text items, so I designed it to concatenate the whole page into one character stream before regex-matching, which means a marker split mid-string is still found; we normalize using the affine transform matrix for position; and we pad the raw text box out to a minimum 140×60 so a signature still fits even if the anchor renders at a tiny font. **Q2. Walk through the club budget lock-on-clerk / deduct-on-dean lifecycle and how concurrent approvals avoid double-spending.**

Each club has two wallets in the `Club` model: a sponsor wallet (`sponsorBudget`, `lockedSponsor`) and an institute-allocated ledger (`allocatedBudget`, `allocatedSpent`, `lockedAllocated`), all `Decimal` columns. I modeled it as a two-phase reserve/commit because a proposal isn't spend yet — it's a promise that has to survive the whole approval chain. Phase one: when the OFFICE_CLERK approves a proposal, we compute available balance as `sponsorBudget − lockedSponsor` (and allocated as budget minus spent minus locked), assert it covers the proposed amounts, and `increment` the `locked*` fields. Phase two: when the DEAN_SW gives final approval, we `decrement` the real `sponsorBudget` / `increment` `allocatedSpent` and release the lock. The double-spend protection is that both the balance check and the mutation happen inside the same Prisma `$transaction`, and the writes use atomic `increment`/`decrement` rather than read-modify-write in app code — so two proposals racing to lock the last of a wallet serialize at the row level, and the second one's sufficient-balance check fails inside its transaction. Financial documents add a reconciliation pass — since the proposal already booked the estimate, the financial approval adjusts `allocatedSpent` by the actual-minus-estimated difference. **Q3. How did you design the faculty-on-leave auto-skip so a document never stalls on an absent approver, and what keeps that loop bounded and idempotent?**

### Model answers

**Q1. Why frame this as RL / D3QN instead of plain cross-entropy, and what does γ=0.75 actually buy when "next state" is just the next EEG window?**

I'll be honest that this is partly faithful reproduction of the IEEE TNNLS 2024 paper I set out to replicate, and partly a genuine design choice about the *loss landscape*. In `fld3qn_subject_dependent.py`, `compute_reward` returns `+1` for a correct action and `-1 - λ/t` (λ=0.1) for a wrong one, and I terminate the episode on the first mistake. That penalty term makes early-in-episode mistakes *cheaper* than late ones (`λ/max(t,1)` shrinks as `t` grows), which nudges the agent to survive longer before erring — a curriculum-like pressure you don't get from flat cross-entropy. The RL framing also gives me a natural non-differentiable reward channel that I later exploit in HARL, where the "reward" is domain-gap-aware, not just label-correctness. As for γ=0.75 in `learn()` — I'll be candid: because next-state is just the adjacent window and the episode is effectively one useful step, the bootstrapped term `γ * next_q_target * (1 - dones)` mostly acts as a mild smoothing/regularizer on the Q-targets rather than modeling real long-horizon return. It stops the target from being a pure one-step reward and couples nearby windows slightly. If I were purely optimizing subject-dependent accuracy, cross-entropy would be simpler; the RL scaffold earns its place as the substrate for the adaptive-RL extension. Why it mattered: it gave me a reward interface I could later hijack to make domain adaptation itself learnable.

**Q2. Walk through the Double-Dueling DQN in `BiFRCNN.forward`: how does `Q = V + A - A.mean()` help, and why does the Double-DQN target reduce overestimation?**

In `BiFRCNN.forward`, after the four `StreamEncoder`s fuse into left/right representations and a shared 128-d layer, I split into two heads: `value_stream` (128→1) and `advantage_stream` (128→n_actions), then combine as `Q = V + A - A.mean(dim=1, keepdim=True)`. The dueling decomposition lets the network learn *how good this EEG state is overall* (V) separately from *which emotion is relatively better* (A). That matters here because for many ambiguous EEG windows the state value is informative even when the two actions are near-tied — the value stream gets gradient signal on every sample regardless of the action taken. Subtracting the mean advantage is the identifiability fix: without it, V and A can drift by an arbitrary constant (you can add c to V and subtract it from every A and get the same Q); mean-centering pins the decomposition so gradients are well-defined. On Double-DQN: in `learn()` I compute `next_actions = self.q_net(next_states).argmax(dim=1)` — the *online* net picks the action — then evaluate it with `self.target_net(...).gather(...)`. Standard DQN uses `max` of the target net for both selection and evaluation, and since the max operator over noisy Q-estimates is biased upward, that systematically overestimates. Decoupling selection (online) from evaluation (target) means a spuriously high estimate for an action only inflates the target if *both* nets agree on it, which is much rarer. Why it mattered: on noisy EEG, overestimation compounds fast, and this kept the Q-targets from blowing up during the 5000-step budget.

**Q3. In phase 2-refined you stack Euclidean Alignment, CORAL, and DANN — what shift does each address, and how did you implement `GradientReversal` and weight the losses?**

Each targets a *different* level of the distribution shift. **Euclidean Alignment** (`euclidean_alignment`) attacks the raw signal geometry: every subject's EEG has a different mean spatial covariance from electrode placement and skull conductivity, so I compute the mean covariance `R` across windows, take `R^{-1/2}` via `eigh` (with `eigvals` floored at 1e-10 for stability), and whiten each window `R_inv_sqrt @ X`. After EA, all subjects sit in a common covariance frame — it's a cheap, unsupervised, first-order fix applied before the network even sees the data. **CORAL** (`coral_loss`) works on the *learned features*: it minimizes the squared Frobenius norm between source and target feature covariance matrices, normalized by `4*d*d` — so it aligns second-order statistics that EA can't, because they're a property of the representation, not the input. **DANN** goes further to *distributional* invariance via adversarial training: `domain_logits` runs the shared features through `grad_reversal` then a subject classifier, and the custom `GradientReversalFunction` is a no-op on the forward pass (`x.clone()`) but returns `-alpha * grad` on backward. So the domain head tries to identify the subject while the reversal makes the feature extractor learn representations the classifier *can't* use — pushing toward subject-agnostic features. I weight both auxiliaries modestly at `LAMBDA_DANN = LAMBDA_CORAL = 0.1` against the TD loss in `total_loss = td_loss + 0.1*dann + 0.1*coral`; I kept them small deliberately so the adversarial and covariance terms regularize rather than dominate the primary Q-learning objective. Why it mattered: this stack is what moved DEAP LOSO from 54.52/56.03% to 56.22/58.78%.

**Q4. HARL uses a PPO actor to output a per-sample CE weight and scales `λ_dann`/`λ_coral` by the batch's mean weight — what's the intuition, and how do FIX-1 and the entropy bonus keep PPO correct and stable?**

The intuition: not every training sample deserves equal say in a cross-subject model — some are prototypical, some are noise. So in `harl_seediv.py`, `RLSampleWeightPolicy` outputs a per-sample weight `w ∈ [0,1]` from a 258-d state (256-d features + domain-gap scalar + prediction confidence), and the supervised loss becomes `(weights * per_sample_ce).mean()`. The key move (`IMPR-2`) is that I then scale `lambda_dann_eff = LAMBDA_DANN * (1 + w_mean)` and the same for CORAL — so when the policy decides this batch is "important," domain alignment gets pushed harder. That's the whole point of *hierarchical* adaptive RL: RL doesn't just reweight the loss, it steers how aggressively I adapt across subjects. On correctness — `FIX-1`: PPO's ratio must be `π_new(a_old)/π_old(a_old)` evaluated on the *action that was actually taken*. My earlier bug evaluated a fresh sample; the fix is `evaluate_old_action`, which calls `rl_policy.evaluate(state, w_old)` to compute `log π_new(w_old)`, and `ratio = exp(new_log_probs - old_log_probs)`, clipped to `[1-0.2, 1+0.2]`. Without that, the importance ratio is meaningless and the surrogate is wrong. The **entropy bonus** (`IMPR-5`): `rl_loss = -min(surr1,surr2).mean() - 0.01*entropy.mean()`. Because the policy is a Normal over a scalar with a learnable `log_std` clamped to `[0.01, 0.5]`, it can collapse to always emitting the same weight, which kills the RL signal. Subtracting entropy keeps `log_std` from shrinking too fast and preserves exploration. I also isolate this in a separate `rl_opt` (`FIX-2/3`) so RL gradients never overwrite the supervised path. Why it mattered: it makes the adaptation strength *learned* rather than a hyperparameter I guessed.

**Q5. Cross-subject is far below the ~85% subject-dependent baseline — how much is fundamental, how did FIX-4 and LOSO prevent inflation, and what would you try next?**

Most of the gap is fundamental, and I want to be precise about why. Subject-dependent, I train and test on the same person's cortex, so ~85% (logs: Val 0.8513/Aro 0.8602 across 10-fold). Cross-subject, the test person is fully out-of-distribution — different cortical folding, impedances, even a different internal strategy for feeling an emotion — so 54-59% on DEAP and 36.03% four-class on SEED-IV (vs 25% chance) is roughly where the calibration-free literature sits; the SOTA I benchmark against, MS-MDA, is only 56.07% on SEED-IV, which I hard-code as the reference line. So I'm near the frontier, not failing. Crucially, that number is *real* because I refused to leak: `global_normalize` computes mean/std from **train windows only** and applies them to test; evaluation is strict LOSO (`train_loso_harl` holds out an entire subject). And `FIX-4` is the subtle one — my `DomainGapEstimator` needs a target centroid, so a naive version would compute it from all test data, quietly leaking the test distribution. Instead `compute_target_centroid` uses only a 10% `CALIB_FRACTION` calibration split with **labels never touched**, and I evaluate on the disjoint `eval_mask` — so the reported accuracy never saw its own labels. What I'd try next: (1) test-time adaptation / entropy minimization on the unlabeled test subject, (2) a small labeled calibration set to quantify how much 30 seconds of calibration recovers, (3) contrastive subject-invariant pretraining before the RL stage, and (4) fixing the `loso_baseline.py` placeholder so the ablation baseline is reproducible from one file. ### Model answers

**Q1. Walk through `attention_block2d` — the theta/phi/psi convolutions, how the sigmoid map is upsampled and multiplied back — and why attention gates over plain concatenation.**

In `attention_block2d(x, g, inter_channel, i)`, `x` is the encoder skip feature and `g` is the coarser decoder feature I'm using as the gating signal. Theta is a `Conv2D(inter_channel, [2,2], strides=[2,2])` on the skip `x` — that stride-2 downsamples the skip to the gating signal's spatial size and projects it into a shared `inter_channel` space. Phi is a `1×1` conv on `g` into the same space. I add them, pass through a `LeakyReLU(0.2)`, then psi is a `1×1` conv down to a single channel followed by a `sigmoid`, giving one attention coefficient per spatial location in the coarse grid. Because theta halved the resolution, I `UpSampling2D(size=[2,2])` that sigmoid map back to the skip's resolution and `multiply` it elementwise onto `x`, so I return a gated version of the skip. All the convs carry `l2(1e-5)` regularization.

Why gates over plain concatenation: concatenation hands the decoder *all* skip features, including irrelevant background, and makes it re-learn what to suppress. The gate computes an additive-attention relevance mask conditioned on the decoder's current context, so before I concatenate, the skip is already scrubbed of activations the decoder doesn't care about. For kidney/tumor/cyst — small foreground on a large abdominal field — that focusing is exactly what improves boundary precision on the rare classes. Why it mattered: it's the difference between the decoder fighting noise and the decoder getting a clean, relevant skip.

**Q2. The four softmax outputs with loss weights 1.0 / 0.25 / 0.25 / 0.25 — what is the guided decoder / deep supervision doing, and how would dropping the auxiliary heads change things?**

In `aru_gd`, the decoder returns `final_out` plus `out_3`, `out_2`, `out_1`. Those three come from `upsample_and_output` taps at successively deeper (coarser) decoder stages — each one is upsampled with `Conv2DTranspose` back to full resolution and given its own `softmax`. In `train.py` I compile with `gen_dice_loss` on all four heads and `loss_weights = {final_output:1.0, out_3:0.25, out_2:0.25, out_1:0.25}`, and the `tf.data` `multi_output_mapper` broadcasts the same one-hot label to all four keys.

What deep supervision buys me: it injects gradient directly into the middle and early decoder blocks instead of forcing every useful signal to backprop all the way from the final head. In a deep residual encoder-decoder that stabilizes training and fights vanishing gradients, and it pressures the intermediate representations to already be segmentation-meaningful rather than just feature soup. The 0.25 weighting keeps them as a regularizing auxiliary signal — the final head at weight 1.0 still dominates the objective.

If I dropped the auxiliary heads: training would likely converge slower and be a bit less stable early on, and I'd expect a small drop on the hard classes where the extra gradient helps most. It probably wouldn't collapse — the model would still train — but I'd lose a cheap regularizer. Why it mattered: it's essentially free at inference (I only use `final_output` in `predict.py`) but pays off during optimization.

**Q3. `gen_dice_loss` combines weighted Dice loss and weighted categorical log loss with class weights `[0.5, 1.0, 3.0, 2.0]` — how did you choose them, and how do the two terms interact for the imbalanced tumor/cyst classes?**

`gen_dice_loss` is literally `weighted_dice_loss(y_true, y_pred) + weighted_log_loss(y_true, y_pred)`. The Dice term is `1 - weighted_dice_score`, where I compute per-class Dice and combine them as a weight-normalized average using `LOSS_WEIGHTS_VEC = [0.5, 1.0, 3.0, 2.0]`. The log-loss term is a categorical cross-entropy where I multiply each class's log term by that same vector before summing.

The weights map to the four classes — background 0.5, kidney 1.0, tumor 3.0, cyst 2.0. I deliberately down-weighted background below one so the vast, easy majority class can't dominate, and I up-weighted tumor the most because it's the smallest and clinically most important, with cyst in between. They're a heuristic ranked by rarity and clinical cost, tuned by watching per-class Dice — not derived from exact inverse frequencies.

The two terms are complementary. Cross-entropy is a per-pixel signal — great gradients early, but with a handful of tumor pixels the background gradient swamps it, which is exactly why I weight it. Dice is a set-overlap signal that's inherently normalized to region size, so it stays meaningful even when tumor is a tiny fraction of the slice, but its gradient gets noisy when predictions are near-empty. Summing them gives me the stable pixel-wise gradient of CE plus the imbalance-robustness of Dice. Why it mattered: it's precisely why tumor and cyst are learnable at all rather than being ignored as rounding error.

**Q4. In `predict.py` you run T=50 passes with dropout forced on and use normalized predictive entropy. Why entropy of the mean rather than mutual information (epistemic vs aleatoric), and how would you validate the maps are calibrated?**

Concretely, I collect `mc_predictions` over T=50 passes with `training=True`, average to `mean_prob`, then `entropy = -Σ mean_prob·log(mean_prob)` normalized by `log(NUM_CLASSES)` to sit in [0,1]. So I'm computing the entropy of the *predictive mean* — the total predictive uncertainty, aleatoric plus epistemic.

I'll be straight about this: I chose entropy of the mean mainly because it's the simplest, most interpretable single scalar per pixel — high entropy means "the averaged model is not confident here," which is exactly the "show me the ambiguous boundary" story a radiologist wants. Mutual information — predictive entropy minus the mean of per-pass entropies — would isolate the *epistemic* part, the model's own ignorance, which is arguably what you most want to flag for out-of-distribution or under-trained regions. I have all 50 passes in memory, so computing MI is basically free, and if I revisited this I'd surface both: entropy for total uncertainty, MI for epistemic. That's the more defensible design.

On calibration — and this is the honest gap — the repo doesn't validate it. Today there's actually a `SENSITIVITY_FACTOR = 3.0` that multiplies the normalized entropy just to make the map redder for display, which deliberately destroys calibration; the raw normalized entropy is the quantity to trust. To validate properly I'd bin pixels by predicted confidence and plot a reliability diagram, compute Expected Calibration Error, and check whether high-uncertainty pixels really coincide with the errors — e.g. does masking the top-uncertainty pixels monotonically improve Dice. If it's miscalibrated, temperature scaling on the logits is the cheap fix. Why it mattered: in a clinical setting an uncalibrated uncertainty map is worse than none, because it invites misplaced trust.

**Q5. `train.py` loads the whole KiTS23 HDF5 into RAM and caps GPU memory via a shard ratio for an H100 NVL. What are the scaling limits, and how would you re-architect the pipeline and move toward a 3D extension without blowing memory?**

Right now I do `f['X'][:]` and `f['Y'][:]` for train/valid/test, so all three splits sit in host RAM as float32, and I set a GPU cap from `ALLOCATED_GPU_MEMORY_GB = (SHARD_COUNT/TOTAL_SHARDS) * 94` — with `SHARD_COUNT=20` that's a ~20 GB logical-device cap on the 94 GB H100 NVL. That's fine for a fixed research dataset on one big box, but the limits are obvious: RAM is the hard ceiling, one-hot masks at NUM_CLASSES multiply the label footprint, startup is slow because nothing streams, and it simply won't hold a full-resolution 3D volumetric set. The shard-ratio cap is also a static heuristic, not something tied to actual model or activation memory.

To fix the 2D pipeline: stream from HDF5 lazily instead of `[:]` — a generator that slices per index, or better a sharded TFRecord layout — and lean on the `tf.data` pipeline I already have (`from_generator`, `map`, `batch`, `prefetch`) so I never materialize the whole set. I'd also drop the `copy_to_device('/GPU:0')` staging, which only makes sense because everything's already resident.

For the 3D extension the README calls out, full volumes won't fit, so I'd switch to **patch-based training** — sample fixed 3D crops (say 128³) around foreground with class-balanced sampling, which also fixes the imbalance sampling problem — and stream those patches. The architecture generalizes: swap Conv2D/Conv2DTranspose for their 3D versions, keep the attention gates and guided decoder, and add mixed precision plus gradient checkpointing to claw back the activation memory that 3D convs eat. At inference I'd do sliding-window patch aggregation. Why it mattered: it's the difference between a slice-level demo and something that respects the through-plane anatomy a real kidney tumor lives in.

**Rapid-fire follow-ups the interviewer might ask next (with 1-line answers):**
- *Why LeakyReLU everywhere instead of ReLU?* To avoid dead units in a deep residual net — with `alpha=0.2` negative activations still pass a gradient, which matters given all the BatchNorm+add residual paths.
- *Your `MonteCarloDropout` differs between the two files — is that a bug?* In `train.py` it forces dropout only when `training is None`; in `predict.py` it always forces `training=True`. Same effect at inference, but the predict version is unambiguous — that's the one that guarantees the 50 passes are actually stochastic.
- *Dropout is only 0.2 and only in the decoder — is that enough MC signal?* It's a modest amount, placed after each decoder res-block; more dropout would give a richer posterior but hurt accuracy, so it's a trade-off I'd tune against calibration rather than guess.
- *Why dilated convolutions in the encoder res-blocks?* The dilation rate grows with depth (1→2→4→8 at the bottleneck) to widen the receptive field without extra downsampling, so I keep spatial resolution while still seeing enough context to localize small tumors.
- *How do you get discrete masks from the averaged probabilities?* `argmax` over `mean_prob` on the last axis gives `pred_labels`; metrics (Dice/IoU/pixel-accuracy) are then computed in NumPy per class against the resized ground truth.
